# VeloxCache 分布式篇学习路线

> 适用前提：你已经掌握单机链路 `Group.Get/Set/Delete -> Cache -> Store(LRU/LRU-2)`。
> 这份文档只解决一件事：把 UA 里剩下的五个层——并发原语层、分布式路由层、网络传输层、服务注册发现层、缓存服务层——串成一条可以自己走通、可以动手验证、可以发现并修复问题的路线。

---

## 0. 先建立正确的心智模型

单机缓存回答的问题是：

```text
这个值在不在我的内存里？不在的话，去哪里回源？
```

分布式缓存多回答三个问题：

```text
1. 这个 key 按规则应该归哪个节点负责？        -> 分布式路由层
2. 我怎么知道现在有哪些节点、谁上线谁下线？    -> 服务注册发现层
3. 我怎么把请求真正发给那个节点，并拿回结果？  -> 网络传输层

另外两个层是横向能力：
4. 并发请求怎么合并、共享状态怎么保护？        -> 并发原语层
5. 上面所有能力被谁编排成一套对外的读写语义？  -> 缓存服务层
```

一句话记忆：

```text
路由层决定"找谁"，注册发现层维护"有谁"，网络传输层负责"怎么问"，
并发原语层保证"问的时候不出乱子"，缓存服务层把它们拼成一次完整的 CRUD。
```

### 分布式读路径（一次远程 Get 的完整生命周期）

以节点 A 读取一个本地没有、且按哈希归节点 B 负责的 key 为例：

```text
 1. 调用方 A：Group.Get(ctx, key)                          group.go:134
 2. A 先查本地 Cache                                        group.go:145
 3. 本地未命中 -> A.load -> singleflight 合并同 key 请求     group.go:278-283
 4. A.loadData -> PickPeer(key)                             group.go:308-311
 5. ClientPicker 用一致性哈希算出 key 的归属节点             peers.go:198-208
 6. 命中 B 且不是自己 -> getFromPeer -> Peer.Get             group.go:313,336
 7. Client.Get -> gRPC 调用 B 的 VeloxCache.Get              client.go:60-72
 8. B 的 Server.Get -> B 自己的 Group.Get                   server.go:158-170
 9. B 本地命中则直接返回；未命中则 B 走 load -> getter 回源
10. 结果沿 gRPC 返回 A
11. A 把结果写进自己的本地缓存（注意：这一步是副本的来源）   group.go:297-302
```

### 分布式写路径（现状）

```text
Set:
  A.Set(key, value)
    -> 先写 A 本地 Cache                                     group.go:178-182
    -> 异步 syncToPeers("set")                               group.go:186,218
    -> PickPeer(key) 只挑出"归属节点" B，发给 B              group.go:224
    -> B 的 Server.Set -> B.Group.Set -> 写 B 本地            server.go:173-190

Delete:
  A.Delete(key)
    -> 先删 A 本地
    -> 异步 syncToPeers("delete") -> 同样只发给归属节点 B
```

这条写路径是理解本项目分布式一致性问题的关键：**它不是广播，只写"本地 + 归属节点"两份**，而且没有任何失效通知（invalidation）。

## 4. 阶段二：服务注册发现层

### 4.1 注册端：`registry/register.go`

```text
Register(svcName, addr, stopCh)
  1. 建 etcd client                                      :27
  2. addr 若是 ":8001"，补成本机 IP ":8001"              :35-42
  3. Grant 一个 10 秒租约                                 :45
  4. Put /services/<svc>/<addr> = addr，并绑定租约         :52-53
  5. KeepAlive 持续续约（心跳）                            :60
  6. 收到 stopCh -> Revoke 租约 -> key 自动消失            :71-76
```

要真正理解的关键词：**租约（lease）+ 心跳（keepalive）**。

节点不是"主动删 key 来表示下线"，而是"停止续约，让 key 过期"。这样即使进程被 kill -9 来不及注销，etcd 也会在租约到期后自动摘除节点。这是分布式系统里"用超时代替可靠通知"的典型思路。

### 4.2 发现端：`peers.go`

```text
NewClientPicker
  -> fetchAllServices()          // 全量拉一次                      :158-178
  -> watchServiceChanges()       // 启动 watch 监听增量             :115-128
     -> handleWatchEvents        // Put 增 / Delete 删               :131-155
     -> set(addr): 建 Client + consHash.Add + clients[addr]        :181-189
     -> remove(addr): consHash.Remove + delete(clients)            :192-195
```

etcd 的 key 设计是 `/services/<svcName>/<addr>`，value 是 `<addr>`。注意 key 和 value 都携带地址，这是后面发现 bug 的线索。

带着这些问题读：

1. watch 收到 Delete 事件时，事件里 `Kv.Key` 和 `Kv.Value` 分别有什么？
2. `parseAddrFromKey`（`peers.go:233-240`）是谁调用的？如果没有被调用，说明什么？
3. `p.selfAddr` 是 `":8001"`，而 etcd 里的 addr 是 `"192.168.x.x:8001"`，两者能比较相等吗？
4. `Close()` 只是 cancel + 关 client，它有没有主动从 etcd 注销？

## 5. 阶段三：网络传输层

三层结构，从上到下：

```text
契约层   pb/velox.proto          Request / ResponseForGet / ResponseForDelete + service VeloxCache
生成层   pb/kama.pb.go          protobuf 消息的序列化/反序列化
         pb/kama_grpc.pb.go     client stub + server 接口
实现层   server.go              实现 VeloxCacheServer，把 RPC 请求转给本地 Group
         client.go              实现 Peer 接口，把方法调用转成 gRPC 请求
```

当前契约（`pb/velox.proto:6-24`）非常精简：

```text
Request { group, key, value }
Get(Request)    -> ResponseForGet { value }
Set(Request)    -> ResponseForGet { value }
Delete(Request) -> ResponseForDelete { value: bool }
```

服务端的关键点：`Server.Get/Set/Delete` 自己不实现缓存逻辑，只做"找 group -> 委派"（`server.go:158-201`）。

客户端的关键点：`Client` 明确实现了 `Peer` 接口（`client.go:23`），所以路由层可以完全不知道 gRPC 的存在——这就是接口解耦。

带着这些问题读：

1. `Client.Set(ctx, ...)` 把 `ctx` 直接传给 gRPC；服务端能读到调用方塞进 `ctx` 的普通 value 吗？
2. `grpc.WithBlock()`、`WithTimeout(10s)`、`WaitForReady(true)`（`client.go:37-42`）分别改变什么行为？
3. 服务端 `MaxRecvMsgSize(4MB)`（`server.go:95`）和消息大小之间是什么关系？
4. 一次 RPC 的 deadline 到了，服务端正在执行的 handler 会立刻停止吗？

## 6. 阶段四：分布式路由层

### 6.1 一致性哈希：`consistenthash/con_hash.go`

核心数据结构（`:14-28`）：

```text
keys         []int          哈希环上的所有虚拟节点哈希值（有序）
hashMap      map[int]string 虚拟节点哈希 -> 真实节点地址
nodeReplicas map[string]int 真实节点 -> 虚拟节点数量
nodeCounts   map[string]int64 真实节点 -> 被路由到的请求数
```

查找过程（`:112-141`）：

```text
hash = hash(key)
二分找到环上第一个 >= hash 的虚拟节点
如果绕过了末尾，回到环头
该虚拟节点对应的真实节点就是归属节点
```

为什么需要虚拟节点：只有 3 个真实节点时，哈希环被切成的弧段长度极不均匀；给每个真实节点放 50 个虚拟节点，等于把每个真实节点切成 50 份撒到环上，负载更均匀（`config.go:20-26`）。

### 6.2 选择器：`ClientPicker.PickPeer`

```text
PickPeer(key)
  -> consHash.Get(key) 得到 addr
  -> clients[addr] 找到对应 Client
  -> 返回 (peer, ok, addr == selfAddr)
```

`isSelf` 是整条读路径的分叉点：`group.go:312` 用它决定"要不要发远程请求"，还是"直接回源 getter"。如果它算错了，轻则多发一次无意义的 RPC，重则自我递归。

带着这些问题读：

1. `Map.Get` 在 `RLock` 下修改 `nodeCounts`（`:137`），这是安全的吗？
2. `rebalanceNodes` 持有 `m.mu.Lock()` 时调用 `m.Remove(node)`，而 `Remove` 又要拿同一把锁，会发生什么？
3. 节点上下线时，`consHash` 的环会变，原本归 B 的 key 可能改归 C。缓存数据会跟着迁移吗？没有迁移的话会怎样？

## 7. 阶段五：并发原语层

这一层在 UA 里对应 `singleflight/singleflight.go`，但实际上面向并发的原语散落在全项目：

| 原语 | 位置 | 保护/实现什么 |
|---|---|---|
| `singleflight.Group` | `singleflight/singleflight.go:15-41` | 同一 key 的并发未命中只真正回源一次 |
| `atomic` 计数器 | `group.go:55-64`、`cache.go:18-21` | 统计、closed、initialized 等"单变量状态" |
| `sync.RWMutex` | `peers.go:37`、`consistenthash:15` | clients / 哈希环等多字段一致性 |
| `sync.Map` | `singleflight.go:16`、`server.go:27` | 并发读多写少的 map |
| `sync.WaitGroup` | `singleflight.go:9,24` | 让跟随者等待首个请求完成 |

singleflight 的关键语义：

```text
Do(key, fn):
  已经有人在执行 key -> Wait，然后复用那次的 val/err
  没有人在执行     -> 自己执行 fn，完成后广播结果并删除 key
```

它防的是**缓存击穿**：某个热 key 突然过期，成千上万并发请求同时未命中，如果都去回源就会打垮数据源。

但要注意它的作用域只有**单个进程**。节点 A 和节点 B 同时对同一个 key 未命中，singleflight 无法跨进程合并，这也是"分布式锁/分布式 singleflight"存在的原因。

带着这些问题读：

1. 如果 `fn` 内部 panic，`c.wg.Done()` 还会被执行吗？等待者会怎样？
2. 为什么在分布式场景下，`Group.load` 合并请求后仍然可能对数据源产生多次回源？
3. `atomic` 保护了 `closed`，为什么还需要 `sync.RWMutex` 保护 `store` 指针和初始化过程？

## 8. 阶段六：缓存服务层汇聚

到这里可以回答"多机上增删改查到底怎么走"了。把当前实现的行为精确记录下来：

| 操作 | 本地 | 归属节点 | 其他节点 | 最终一致性 |
|---|---|---|---|---|
| `Get` 命中本地 | 直接返回 | 不访问 | 不访问 | 可能读到旧副本 |
| `Get` 未命中 | 向归属节点要 | 命中则返回，未命中回源 getter | 不访问 | A 会把结果缓存成副本 |
| `Set` | 写入 | 写入（异步） | **不通知** | 其他节点的旧副本不失效 |
| `Delete` | 删除 | 删除（异步） | **不通知** | 其他节点可能继续返回已删值 |
| `Clear` | 只清本地 | 不通知 | 不通知 | 各节点视图不一致 |

所以当前项目本质上是一个 **"本地缓存 + 归属节点回源 + 单播写同步"** 的模型，而不是严格意义上的分布式一致性缓存。它保证的是"同一个 key 的读写都倾向于围绕归属节点发生"，但不保证"所有节点看到同一个值"。

理解这一点，你就知道"完善剩下的项目"真正的方向是什么：

```text
1. 定义一致性目标：允许 TTL 内的最终一致，还是要写后读一致？
2. 写路径：单播改成广播失效（invalidate），还是引入版本号/逻辑时钟？
3. 读路径：命中旧副本怎么办？要不要 read repair？
4. 节点变更：环变化后数据如何迁移，或如何用 TTL 兜底？
5. 故障处理：归属节点不可用时，回源还是返回错误？超时/重试/熔断策略是什么？
```

```text
阶段 3 网络传输：  能说清 proto -> stub -> handler -> Peer 接口的映射，
                   并解释哪些信息不能过网（context value、goroutine 本地状态）
阶段 4 路由：      能手工计算一个 key 落在环上的哪个虚拟节点、为什么 isSelf 关键
阶段 5 并发原语：  能举出"atomic 够用"和"必须用锁"各两个本项目中的例子
阶段 6 服务汇聚：  能准确说出当前多机 Get/Set/Delete 的一致性语义与缺口，
                   并给出一种你选择的完善方案（广播失效 / 版本号 / TTL 兜底）
```

## 12. 建议的推进节奏

```text
第 1 步：装配 + 注册发现（读 + 跑起来，半天）
第 2 步：网络传输（读 proto/生成代码，自己写一个外部 Client 调用节点，半天）
第 3 步：分布式路由（手工算哈希 + 验证 PickPeer 的 isSelf，半天）
第 4 步：并发原语（读 singleflight + 修 panic 安全，半天）
第 5 步：服务层汇聚（画出多机 CRUD 时序图 + 选一个一致性问题动手修，1~2 天）
```

每一步都以"能讲清楚 + 能跑出日志 + 能改一处代码"作为完成标准，而不是"读完了"。
